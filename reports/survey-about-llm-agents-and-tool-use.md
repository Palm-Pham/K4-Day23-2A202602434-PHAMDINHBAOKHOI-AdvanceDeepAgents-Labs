# Survey: LLM Agents and Tool Use

## Synthesis by theme

### 1. What an LLM agent does when it uses tools

An LLM agent is usefully distinguished from a fixed workflow by who chooses the next step: a workflow follows predefined control paths, while an agent lets the model direct some of its own process and tool use. This flexibility is valuable for open-ended tasks, but adds latency, cost, and opportunities for error; a single model call or simpler workflow is often the better starting point when it is adequate [1]. In a typical tool-use loop, the application supplies tool descriptions, the model emits a structured call, the application executes it, and the result returns to the model, which may call again or respond to the user [2].

The central design problem is therefore not simply whether a model can produce a plausible tool call. It is whether the whole system can select a suitable tool, provide valid arguments, interpret real tool feedback, recover from failure, and stop once the user's goal is met. Tool use moves parts of the task into an environment whose state and output the model does not fully control; evaluation of multi-step agents accordingly finds failures in long-term reasoning, decision-making, instruction following, and action formatting [3][4].

### 2. Interaction patterns and architecture

**Reason-and-act loops.** ReAct established a simple but influential pattern: interleave model reasoning with task-specific actions. Its trajectories include actions and environment observations; reasoning can update a plan, actions retrieve information or interact with an environment, and observations inform subsequent steps. The paper reports improved outcomes over its cited baselines on knowledge-intensive QA and fact verification, and absolute success-rate gains of 34% on ALFWorld and 10% on WebShop over cited imitation/RL methods [5]. Browser-assisted question answering makes the loop concrete: WebGPT searched, clicked, found text, scrolled, and captured quotations in a browser environment, then used collected references to compose its answer [6]. In embodied code environments, Voyager instead made executable code its action space, used execution feedback to refine programs, and stored successful programs as retrievable skills [7].

**Schema-bound function/API calling.** Production-style function calling narrows the action space by describing available functions and their arguments with JSON Schema. The model can select a function and return structured arguments; the application, not the model, actually performs the call and returns its output [8][2]. Schema adherence reduces malformed-call risk but does not guarantee that a call is relevant, authorized, semantically correct, or sufficient to complete a multi-step task. With many candidate tools, deferred tool search can avoid loading every description into context at once [2].

**Learning when and how to call tools.** Toolformer generates candidate API calls in text, filters them according to whether they improve future-token prediction, and fine-tunes on retained sequences of text, calls, and results. The investigated APIs include question answering, search, calculation, translation, and calendar operations [9]. Gorilla addresses a different difficulty: API documentation changes and models may hallucinate calls. Its retrieval-aware training supplies API documentation alongside requests, and its benchmark spans APIs associated with Hugging Face, TorchHub, and TensorHub [10]. These methods make tool descriptions and retrieval part of the model's decision context rather than assuming a fixed, memorized API inventory.

**Planning and orchestration.** Some systems separate high-level planning from execution. HuggingGPT uses an LLM controller to decompose a request, select expert models, execute subtasks, and synthesize results, including across modalities [11]. ToolLLM's ToolBench represents single- and multi-tool instructions as API-call paths, while its DFSDT method explores multiple reasoning traces during solution construction and a retriever helps select APIs [12]. These architectures illustrate a spectrum: direct calls work for simple, well-specified requests; explicit decomposition, retrieval, and execution feedback become more important as tasks span multiple tools or dependencies.

### 3. Training data and capability building

Tool-use capability is shaped by both model training and orchestration. Toolformer demonstrates self-supervised generation and filtering of tool-use examples, while API-Bank describes generated tool-use dialogues and fine-tuning Alpaca-7B into Lynx. In its evaluation, performance generally declined as the task expanded from API calling to API retrieval plus calling and then planning plus retrieval plus calling, underscoring that these are distinct competencies [9][13].

For breadth across interfaces, ToolBench contains 16,464 REST APIs across 49 categories, with generated instructions and solution paths for single- and multi-tool tasks. ToolLLaMA is fine-tuned on the resulting data; the system combines API retrieval with a search procedure that considers multiple candidate action traces [12]. Gorilla's APIBench and retrieval-aware training focus more specifically on generating correct API calls from documentation; the reported test-time retrieval limitation makes clear that a trained model cannot compensate reliably for poor retrieval inputs [10].

Training on interaction trajectories is not equivalent to robust autonomous performance. WebGPT combines imitation learning and human-feedback optimization for browser-based answering, but still operates within a defined browsing environment and task setup [6]. Across these approaches, data generation, tool documentation quality, retrieval, the format and accuracy of tool responses, and the inference-time control loop jointly determine what the agent can do. The evidence supports treating those as a system-level capability stack rather than attributing success solely to the base model [12][10][13].

### 4. Evaluation: from call accuracy to long-horizon outcomes

A useful evaluation ladder distinguishes (1) whether a call is syntactically valid, (2) whether the right API and arguments were chosen, (3) whether a sequence of calls solves the task, and (4) whether the system does so reliably under state changes, ambiguity, and adversarial inputs. APIBench evaluates API-call correctness and functional behavior, whereas ToolBench's ToolEval uses pass rate and preference judgments over action sequences; the ToolLLM paper reports imperfect agreement between its automatic evaluator and human judgments [12][10]. API-Bank evaluates planning, retrieval, and calling in runnable-tool dialogues and observes that performance degrades as more stages are combined [13].

Interactive benchmarks broaden coverage beyond isolated calls. AgentBench spans eight environments, including operating systems, databases, games, household tasks, shopping, and browsing, using multi-round tasks and environment-specific metrics [3]. ToolSandbox adds stateful tool execution, implicit dependencies, conversational interaction, and milestone scoring along trajectories; it reports that state dependencies, canonicalization, and insufficient information remain difficult [4]. These benchmarks measure capabilities closer to agent behavior, but scores remain tied to the particular environments and task distributions they instantiate.

Tool evaluation also has a reproducibility problem: live APIs change or become unavailable. StableToolBench responds with a virtual API server, cached responses, and API simulators; the paper reports that only 44.4% of scanned ToolBench API calls succeeded at the time of its scan. It proposes solvability-conditioned pass and win rates to separate task difficulty from unavailable services [14]. Newer operational benchmarks address breadth and realism from different directions: MCP-AgentBench describes 33 operational MCP servers and 188 tools across 600 queries [15], while Tool Decathlon covers 32 applications and 604 tools, with realistic multi-application tasks averaging about 20 turns. In the reported evaluation, the best model completed 38.6% of tasks, indicating substantial headroom on long-horizon workflows [16].

No single score captures all relevant qualities. Benchmarks should report call validity and task completion, but also partial progress, failures, tool availability, cost or interaction budget, and reproducibility. Stateful evaluation helps reveal dependencies that static call accuracy misses, while separate task-solvability accounting can prevent infrastructure failures from being mistaken for model errors [14][4].

### 5. Deployment patterns, costs, and interoperability

A sound design begins with the simplest architecture that meets the need. Fixed workflows and prompt chains are appropriate where steps are predictable; routing can send distinct requests to specialized paths; parallelization is useful for independent subtasks; orchestrator-worker designs fit tasks whose subtasks emerge dynamically; evaluator-optimizer loops help when results can be judged against clear criteria [1]. Each added agent or model call creates another place for latency, expense, context loss, or coordination failure, so human checkpoints and explicit stopping conditions are practical controls as well as usability features [1].

Multi-agent systems can improve breadth when independent work can be delegated, but they are not a universal upgrade. Anthropic describes a research system in which a lead agent plans and synthesizes parallel specialist work; it reports that agent systems used about four times the tokens of chat interactions and multi-agent systems about 15 times. Its internal evaluation also reported better performance than a single-model comparison. The report notes that shared context and tightly dependent subtasks are poor fits, and that overlapping delegation and excessive status updates can waste effort [17]. Those results are system- and evaluation-specific, but clarify the tradeoff: parallelism buys coverage only where tasks genuinely decompose.

Tool interfaces are themselves an architectural choice. A survey of interoperability protocols characterizes MCP as a client-server interface for tool invocation and typed data exchange, ACP as REST-based structured messaging, A2A as peer-to-peer task delegation, and ANP as decentralized discovery and collaboration. It presents these standards as evolving rather than a settled universal stack [18]. Operational evaluations centered on MCP tools further suggest that benchmarks need to account for real server behavior, tool heterogeneity, and long descriptions that can consume context [15][16]. Protocol adoption can simplify integration, but does not by itself establish that a tool is safe, reliable, or correctly selected.

### 6. Reliability and security

Tool access creates a trust boundary. A model may encounter instructions embedded in webpages, email, documents, or images that conflict with the user's request. If untrusted content can influence a privileged agent that has access to private data or consequential tools, prompt injection can lead to unauthorized actions or disclosure. AgentDojo evaluates agents using multiple tools over untrusted content in stateful tasks; it also reports that leading systems solve fewer than 66% of tasks even without attacks, so baseline reliability and adversarial robustness must be measured separately [19].

Mitigations should be layered and enforced by the surrounding system rather than relying only on the model to recognize malicious instructions. Design patterns include least-privilege tools, isolating the processing of untrusted inputs, restricting how such inputs can influence later actions, sandboxed execution, and user confirmation for sensitive operations [20]. CaMeL illustrates a stronger separation: a privileged component generates task control flow, while a quarantined model processes tool-returned untrusted content; a system layer tracks data dependencies and checks policies before tools execute. Its reported AgentDojo results show a security/utility tradeoff—77% of tasks solved with provable security versus 84% for an undefended system [21].

Practical computer-use guidance reflects the same principles: isolate execution in a dedicated VM or container, minimize privileges and sensitive data, restrict network destinations, ask for confirmation before consequential actions, and verify that actions actually succeeded rather than trusting the model's assumption [22]. Claude Code's documented controls similarly include read-only defaults in manual mode, approvals for modifying actions, sandboxing and network restrictions, and explicit permissions for external servers and commands [23]. These are deployment patterns, not proof against every attack; tool outputs, server behavior, and user-approved actions remain relevant risks.

### 7. Synthesis and open problems

The field has progressed from prompting models to alternate thoughts and actions toward a broader systems discipline: structured interfaces, retrieval over tool catalogs, explicit orchestration, stateful execution, and security controls now shape agent behavior alongside model capability [5][12][2][18]. The strongest conceptual distinction is between *making a call* and *reliably completing a task*: the latter requires selection, planning, execution, observation, verification, and safe stopping across a potentially changing environment [13][3][4].

Three priorities follow from the evidence surveyed. First, evaluation should combine realistic task completion with reproducible tool behavior and intermediate-state diagnostics, while reporting costs and unavailable services [14][4][15][16]. Second, tool access should be narrowly scoped and mediated by deterministic policy, sandboxing, and human confirmation for high-impact operations, especially when models process untrusted content [19][21][20][22]. Third, architectures should scale adaptively: expose only relevant tools, use workflows when tasks are predictable, and reserve autonomous or multi-agent orchestration for tasks whose uncertainty or parallel structure justifies its cost [2][1][17].

A consequential open challenge is sustained performance over long sequences and changing state: current benchmarks show that even strong models struggle with multi-step tool dependencies and cross-application tasks [4][16]. Another is security without unacceptable utility loss: tested defenses can reduce attack impact but may block benign task completion or fail against adaptive threats [19][21]. Finally, interoperability needs to mature together with capability discovery, permissions, and measurement; standardizing the mechanics of tool exchange is only one piece of building agents that can be trusted to act [18][15].
